- **G-ORBITAL-SHELL-TYPESCRIPT-025** — The kernel-hosted client's production build needs a raised Node heap, and the client ships the whole resolved program. Measured 2026-10-18 on `vite build` of `packages/client` (default Node heap): `std-crm` dies with `JavaScript heap out of memory` (peak RSS 5.2 GB) while `build.sourcemap: false` builds it at 4.19 GB RSS; `std-browse` (25 rows) peaks at 5.2 GB with the template's `sourcemap: true` and 3.85 GB without. The program is not the cause: inlining `program.json` costs about 0.35 GB (`std-crm` 4.19 GB against `std-browse` 3.85 GB, both without maps), and `build.json.stringify: true` changes nothing. The heap goes to the template's `sourcemap: true` over a 9 to 13 MB main chunk (`@almadar/ui` and its libraries; maps are 27.6 MB). Separately the client carries the full program: `std-crm` 4,580,950 B (gzip 605 KB, brotli 185 KB; traits 84 %: state machines 1.71 MB, of which effects 1.11 MB, config 1.54 MB), `std-studio` 9,139,167 B (gzip 1.22 MB, brotli 227 KB). Never read by a client render and droppable by a declared client-program contract: `_metadata` 253 KB and `ledger` 137 KB (`std-crm`), descriptions, synonyms, labels and tiers about 0.8 MB, `effectRow` 36 KB, event ids; stripping those leaves 2.9 MB (gzip 315 KB). No `instances` seed rows or vectors are in either program. Decisions open: a smaller or no source map for the client build in the template (or a raised heap in the template's `build` script), and whether the client program becomes a separate derived asset (`program.client.json`, fetched and compressed, parsed once). orbital-shell-typescript kernel host (`kernel_host.rs`, the template `vite.config.ts` `build.sourcemap`) [architectural] — evidence: `orb compile packages/almadar-behaviors/behaviors/lolo/app/organisms/std-crm.lolo --shell typescript --host kernel`, then `npx vite build` in `packages/client` with and without `sourcemap`. Prevention rung 3 (`orb verify --compiled` builds the client at the default heap). found 2026-10-18

- **G-ORBITAL-SHELL-TYPESCRIPT-013** — After a mutation, a generated server re-sends a `ref`'s rows as the ref's own filtered page only when the ref's filter reads nothing but `@user`/`@config` and every ref of that entity agrees. A filter reading `@payload`/`@entity`, a ref by id, or a non-literal limit still re-sends the viewer's whole `@read`-scoped set, because the refreshing handler cannot evaluate another handler's request bindings. Also, the generated `pushUpdate`/`pushDelete` refusal path (policy false → no write, `@update denied`) is so far checked only by type, never run. Fix: carry the ref's resolved query (bindings applied at load time) with the ref so a refresh replays it, and add a generated-app test over `CountingPersistence` asserting one `queryPage` per refresh and a refused guarded write. `orbital-shell-typescript` [architectural] — evidence: S9 follow-up 2026-10-14; prevention rung: none of the language rungs (generated host behavior), gated by the generated-app test.

- **G-ORBITAL-SHELL-TYPESCRIPT-016** — machine emits fan out over the embed chain on the compiled path. Generated hooks emit through `useEventBus()` (the TraitScopeProvider-wrapped bus), so every qualified `UI:` key an effect publishes (`emitCascadeEvent`, implicit targets, the bridge echo) is re-emitted once per ancestor scope (`UI:<orbital>.<ancestor>.<EVT>`). EXEC-SEED-3 says only a UI-originated seed bubbles; listens/emits go to a single scope. `@almadar/ui` already has `useRootEventBus` for "a machine-originated relay", but it is not exported from `hooks/index.ts`, and generated apps install `@almadar/ui` from the registry. Fix: export it from `@almadar/ui` (publish via cascade), then the generated `useOrbitalBridge` (`backend/client/bridge.rs:601`) and the shared hooks (`shared_trait_logic.rs:449,549`) use the root bus for machine emits; seed clicks keep the scoped one. Twin test against the kernel's `dispatch_seed` (ancestors only for the seed). Since the 015 fix (2026-10-15) the duplicate deliveries it caused are gone because `claimDelivery` dedupes one physical emit's keys; what remains is the ancestor keys themselves. `[architectural]`
